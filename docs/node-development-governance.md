# DIYIME2 Node 開発・運用規則 v1.0

- **状態**: 採用済み（2026-11-04）
- **適用範囲**: `pitapa79/DIY_IME_node` の新規Issue・開発・レビュー・配布・保守
- **採用経緯**: [Node #17](https://github.com/pitapa79/DIY_IME2_node/issues/17)／ユーザー承認
- **原則**: ノードごとに長期管理し、実装変更は短期タスクとして完結させる。仕様・採用はユーザー、承認済み範囲の技術実装はAIに委任する。

この文書はNodeリポジトリ固有の運用を定める。共通ABI・データ契約・実行エンジン・権限・セキュリティ・OS接続の正本は[DIY_IME本体](https://github.com/pitapa79/DIY_IME)にあり、Node側で重複した別規格を作らない。[ノード分類](node-classification.md)は「役割」を表す用語の正本であり、この文書の実装状態・採用状態と区別する。

## 1. 判断権限と基本姿勢

1. ノードの新しい機能・外部に見える仕様・公式採用・標準同梱・権限方針の**最終判断者はユーザー**とする。
2. Codex・Claude等のAIは改善や不具合を発見し、Issueを自由に**提案・作成**できる。ただし**Issue作成≠実装許可≠公式採用≠配布許可**である。
3. 実装開始には、ユーザーの明示指示、承認済みIssue・親Issueで明確に委任された作業、または事前に承認された軽微修正の対象範囲のいずれかが必要。推測で承認範囲を広げない。
4. 承認済みの変更について、内部実装方法・モジュール分割・テスト追加・非公開の最適化はAIが判断してよい。依存ライブラリの追加はライセンス、供給元、ビルド再現性、セキュリティ、配布影響を検査し、承認範囲外なら確認する。
5. AI間で担当を変更したり並行開発したりしてよいが、別エージェントを自動起動することは明示依頼された場合に限る。ユーザーの現在の指示は本規則より優先する。
6. 未採用ノードの**実験的な実装**は、実験そのものが承認されていれば可能。実装しただけで正式採用・既定有効化・標準同梱に昇格しない。

## 2. Issue体系

Issueは以下の種類に分ける。ラベルを利用できる場合は種類を識別する（推奨名を記すが、ラベル未作成の環境ではタイトルと本文で区別できるようにする）。

| 種類 | 推奨ラベル | 用途 | 完了・クローズ |
| --- | --- | --- | --- |
| Node管理 | `type:node` | 1ノードの長期的な入口・履歴 | 原則保守期間中はOpen。廃止・移行確定でClose |
| 開発 | `type:task` | 新規ノード・機能追加・リファクタリング | 受入条件達成でClose |
| 不具合 | `type:bug` | 再現・原因・修正・回帰テスト | 修正確認、または理由を記した対応終了でClose |
| 共通基盤 | `type:infrastructure` | Node側のSDK取込・ビルド・テスト・パッケージ/CI等 | 受入条件達成でClose |
| 提案・設計 | `type:proposal` | 未確定の機能・仕様・運用案を議論 | 採否・後続Issueへの引継ぎを記録してClose |

セキュリティ案件には種類に追加してセキュリティ識別を行う。公開Issueへ秘密・未公開の脆弱性詳細を書き込まない。状態ラベル（例：`status:proposal`, `status:approved`）は任意の補助情報であり、**本文・コメントの承認記録なしにラベルだけで実装を許可しない**。

### 2.1 1ノード＝1管理Issue

- 同じ安定したノード識別子（`kind`）につき管理Issueは原則1つ。言語別実装・版・保守タスクごとに管理Issueを増殖させない。別のノード識別子として提供するなら別件。
- タイトル例: `[Node] text.romaji-to-hiragana`。
- 本文に**kind、目的、分類、実装状態、採用状態、ソース・契約・利用例へのリンク、保守方針、関連Issue/PR、既知の制限**を記載する。
- 仕様・契約・バージョンの正本はリポジトリ内のファイルに置き、Issueはリンクを集約する**索引**とする。本文に仕様の別コピーを蓄積しない。
- 管理Issueは「未完了タスク」ではない。Open Issue集計で作業の残数を把握するときは `type:node` を除外する。ラベルがない場合は `[Node]` タイトルで見分ける。
- 既存48登録ノードと2試作ノードの管理Issueは**必要に応じて段階的に**作成する。一括登録を必須としない。作成前に同一kindの既存管理Issueがないか確認する。
- 管理Issueを閉じても、コード・配布物を自動削除しない。

### 2.2 作業Issue・提案Issue

各作業Issueは、目的、対象ノード/ファイル、要求動作、完了条件、対象外、依存先（他Repoを含む）、承認状況を明示する。仕様と受入条件が未確定なら提案Issueとして扱い、勝手に実装Issueへ移行しない。

作業は原則として独立して受け入れられる粒度で切る。1つの変更が複数ノードへ及ぶ場合、共通原因・共通目的なら1つの基盤/作業Issueでよい。関連する管理Issueすべてからリンクする。

**AIはIssueを作成できるが、作成を理由に作業開始しない。** 未承認の新機能や仕様変更は、ユーザーの採否判断を待つ。安全性に直結する緊急問題は、被害抑止と判断に必要な情報を先に報告し、承認済みの修正権限を超えない。

### 2.3 承認の記録と自動着手

- 実装開始の承認は、対象Issueのコメント、親Issueの委任範囲、ユーザーによる明示的な指示のいずれかに追跡可能な形で残す。
- **軽微な修正の自動着手は、事前に承認した対象・変更種別・制約・テスト条件の範囲内だけ**とする。包括的な無制限自動実装を認めない。
- 作業途中で新しい公開仕様、データ互換性の変更、新しい権限や本体API、未承認の依存関係が必要になったら、別Issue/依存Issueとして提案し判断を待つ。

## 3. ブランチ・PR・レビュー・マージ

- **1作業Issue → 原則1短期ブランチ → 原則1PR**。管理Issueや純粋な提案Issueに恒久ブランチを割り当てない。
- 大規模Issueは受入範囲と依存関係を明示し、複数PRに分けてもよい。途中PRでは `Refs #番号`、完了するPRでは `Closes #番号` を用いる。後日の改善は新しいIssueを起こす。
- ブランチ例: `codex/24-add-c-wasm-node`、`claude/31-fix-kana-conversion`。担当交代時にブランチ名を改名する必要はない。並行担当は別worktree/cloneを使う。
- PR本文には対象Issue、実装内容、テスト結果、未実行検査、互換性・権限・性能への影響、既知の制限、必要なら引継ぎSHAを書く。
- AIがコードレビュー・差分確認を担当する。可能な限り実装担当と異なるレビュアーを用い、CIとコードレビューを**別物**として扱う。AI自身の自己レビューは独立レビューと表現しない。
- **技術的なマージは統合担当AIに委任できる**。条件は (a) 承認済み範囲 (b) 必須CI成功 (c) 重大なレビュー指摘なし (d) 依存関係解決 (e) 仕様・採用・配布判断の追加承認が不要、の全て。満たせなければマージせず報告する。ユーザーが個別にマージ権限を留保した指示を優先する。
- **ユーザーの別途承認を要する**: ノードの公式採用、標準同梱の新規決定、本体API/公開動作の破壊的変更、権限・セキュリティ方針の変更。技術レビューで代行できない。

## 4. 実装状態・採用状態・分類

3つの独立した軸を混同しない。

1. **分類**: システム／プリミティブ／標準機能（用語の意味は[分類定義](node-classification.md)を参照）。分類名は実装・配布・権限の許可を意味しない。
2. **実装状態**: `設計中` → `試作中` → `実装済み` → `検証済み` → `保守中` → `廃止`。必要に応じて段階を飛ばしてもよいが、証拠なしに検証済みとは呼ばない。
3. **採用状態**: `未採用`／`実験用`／`公式採用`／`標準同梱`。公式採用と標準同梱は**別の承認判断**。技術的な検証成功やパッケージ生成は自動採用を意味しない。

既存の試作ノードは明示的に採用・登録するまでopt-inのままにする。過去の実験的な登録状態を新ルールで勝手に「正式採用」に改めない。

## 5. ノードの実装・言語・契約

- 言語は原則自由。現在のHostが受け入れる実行形式・外部ABI・データ契約に適合することが必須。Rustの内部 `Node` traitは外部言語向けABIではない。
- 新しい言語はまず独立した検証Issueとテスト用ノードで、実Wasm互換性、Unicode、NoOutput、エラー、設定、メモリ所有権、サイズ/時間上限、隔離実行を確認する。その結果は「公式言語SDKとしてサポート済み」を自動的に意味しない。
- 公開 `kind`、バージョン、ポート、スキーマ、既定設定、Data/NoOutput/Error、正式fixtureの意味を維持する。実装を通すための期待値の弱体化は不可。変更が必要なら独立した承認・移行計画を要する。
- **ノードごとの独立バージョン管理を目標とする**。機能契約のバージョン、対応Host API、パッケージ/ビルド識別子は区別する。現行の公式48パッケージは共通Wasmモジュールを含むため、現時点で独立ビルド・独立更新が実現済みとは主張しない。
- 単体・契約・回帰テストを必須とし、入力の正常/空/不正、Unicode、NoOutput、エラー、設定・ポート・データ構造を検証する。辞書・通信・秘密・OS/権限を扱う場合は、該当する隔離・許可・取消・資源テストを加える。具体的なコマンドは[README](../README.md)とCIに従う。
- 個別Node担当は原則自分の実装・個別テスト・使用例だけを変更し、共通登録・SDK・依存関係・パッケージ・CIは統合担当が管理する。担当Issueが別途明示した場合はその範囲に従う。

## 6. 本体との責務境界・セキュリティ

| 担当 | 責務 |
| --- | --- |
| Nodeリポジトリ | 個別処理、Node固有仕様/契約/検査、ノード配布データ生成、Node管理Issue |
| 本体リポジトリ | 共通ABI・SDK正本、グラフ実行、Worker隔離、権限/秘密/通信/OS境界、IME/TSF、パッケージ受入/実行許可 |

- Nodeが本体API変更を必要とする場合、**本体側へIssueを作り、ユーザー承認後に本体で変更**する。Node側の依存Issueと相互リンクし、レビュー済み固定SDKを取り込む。Node担当は `sdk/runtime` を直接変更しない。
- Nodeの処理分類や公式配布状態によってOS権限を自動で与えない。実際のファイル・ネットワーク・秘密・入力情報の流れに対する本体の承認・隔離・停止ルールを守る。
- 権限要求の増加、外部データ送信、秘密へのアクセス、ネイティブ実行等は、導入前に目的と経路を可視化し必要な承認を取得する。

## 7. 採用・配布・更新・廃止

- 公式採用時は、機能範囲、保守責任、契約、依存、テスト、セキュリティ条件を記録しユーザー承認を得る。**公式採用≠標準同梱**。
- 標準同梱の判断は別途承認する。配布物は既存のパッケージ検証、出自・ハッシュ、互換性、実行時の個別権限確認を省略しない。実験・未登録ノードを黙って同梱しない。
- 更新は新しい作業Issueで行い、管理Issueに結び付ける。互換性を破る変更は別バージョン・移行方法・既存グラフへの影響を説明する。
- 廃止は利用者・既存グラフ・代替機能への影響を検討して承認する。管理IssueのCloseとコード/配布物の削除は別操作とする。

## 8. 移行・変更管理

1. **本規則は採用後に開始する新規作業から適用**する。既存Issue・PR・履歴・ブランチを遡及的に無効化・改名・再整理しない。進行中の作業は既存の承認範囲で続け、次のタスクから新方式を使う。
2. 既存ノードの管理Issueは段階的に設ける。既存48件の一括Issue作成はしない。
3. 規則の改善はAIもIssue/PRで提案できるが、**承認権限・自動着手権限・セキュリティ基準を勝手に拡大しない**。変更にはユーザー承認を要する。
4. Node固有運用は本書を正本とする。本体の共通仕様と矛盾する場合は本体側が優先し、両方のIssueへ差異を記録して解消する。

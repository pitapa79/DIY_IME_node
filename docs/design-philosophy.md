# DIY_IME 設計思想

DIY_IME は、完成した基盤を使うユーザーが、ノードを作成・選択・組み合わせて、自分の作りたい IME を構成できることを最優先する。

ここでいう「ユーザー」は DIY_IME 本体の開発者ではなく、完成した DIY_IME 上で IME を構成し、利用する人を指す。

## 1. ユーザーが作りたい IME を、DIY_IME 側の都合で制限しない。

✕ 「重いから LLM は1個まで」「この処理順は禁止」と本体側で決める。  
◯ 重い構成も許可し、必要ならタイムアウトや分岐をユーザーが設定できるようにする。

## 2. 本体は小さく、能力は外へ出す。

✕ SKK、LLM、音声入力、特殊変換などをすべて本体へ組み込む。  
◯ 本体は実行基盤に徹し、個別の能力はノードなどの交換可能な部品として提供する。

## 3. 処理は交換可能にする。

✕ 「かな→漢字変換はこのエンジンを使う」と本体に固定する。  
◯ 変換、辞書、入力方式、後処理などをユーザーが自由に差し替えられるようにする。

## 4. 実装ではなく、境界を標準化する。

✕ すべてのノードに本体と同じ言語・ライブラリ・実装方式を要求する。  
◯ 入力・出力・状態・エラーなどの接続方法を定め、その中身の実装方法はできるだけ自由にする。

## 5. 処理の流れを見えるようにする。

✕ 「なぜこの候補になったのか」「どこで遅くなったのか」が分からない。  
◯ データの流れ、ノードの出力、実行時間、エラーなどを確認できるようにする。

## 6. 制限するのではなく、制御するための手段を提供する。

✕ 「500 ms を超える処理は禁止する」と本体側で一律に制限する。  
◯ 処理開始からの経過時間を出力するノードなどを提供し、500 ms で打ち切るか、待ち続けるかをユーザーが決められるようにする。

たとえば巨大な IME 構成自体は否定しない。その代わり、経過時間の観測、タイムアウト、分岐、フォールバックなどを構成側から扱えるようにする。

## 7. ユーザーが IME を構成できることを前提に設計する。

✕ 開発者が想定した数種類の IME から選ばせる。  
◯ ノード、辞書、変換規則、処理順序などを組み合わせて、ユーザー自身が IME を作れるようにする。

## 8. 未来を決めつけないが、未来を不必要に閉ざさない。

✕ 「将来 Linux 対応するかもしれない」だけで、今から巨大なクロスプラットフォーム層を作る。  
✕ Windows 専用だからという理由で、OS 依存処理を本体全体に散らす。  
◯ 今必要な Windows 版を素直に作りつつ、OS 依存部分など明確に分離できるものは分離しておく。

---

要約すると、DIY_IME は **ユーザーの選択を制限するのではなく、その選択を実現・観測・制御するための手段を提供する**。

# DIY_IME2 — ノード分類の用語定義

- 状態: **用語の定義を採用**（個別ノードの標準採用・実装を意味しない）
- 適用範囲: DIY_IME2本体、将来のノード開発、Issue・ドキュメントにおける共通の呼称
- 関連: [設計思想](design-philosophy.md) / [コア設計](https://github.com/pitapa79/DIY_IME2/blob/1a385a9d9bfe0d2bcf083bf3bec35901a8d30133/docs/core-architecture-v0.1.md) / [汎用ノード候補](https://github.com/pitapa79/DIY_IME2/blob/1a385a9d9bfe0d2bcf083bf3bec35901a8d30133/docs/generic-node-candidates.md)

## 基本的な考え方

**ノードが何を担当するか**で分類する。開発言語、処理速度、組み込みか外部プラグインか、実装済みかどうかは分類の根拠にしない。

| 分類 | 定義の要点 | 代表例（各ノードの仕様・採用状況は別途判断） |
| --- | --- | --- |
| **システムノード** | ノードグラフとDIY_IME2の実行環境・ホスト・OSとの**接点**を提供する | Input、Output、Spec、将来のUI |
| **プリミティブノード** | ほかの処理と組み合わせて使える、**小さく汎用的な基本操作**を提供する | 文字列置換、比較、条件分岐、Choice生成、スコア加算 |
| **標準機能ノード** | DIY_IME2側が共通利用のために**標準提供する、ひとまとまりの実用機能**を提供する | ローマ字→かな変換、特定辞書の検索、かな漢字変換、翻訳など |

### 1. システムノード（System Node）

ノードグラフ単独の文章処理では得られない、**実行環境との入出力やホスト提供情報・サービスへの接続**を担うノード。

- **Input**: 固定文字列またはホストから受け取ったキーボード由来文字列をグラフに流す。
- **Output**: `print()` / `debug.log` 相当の出力・観測を行う。IMEとしての最終出力先とは限らず、ログやベンチマークにも利用する。
- **Spec**: CPU・GPU・RAM・VRAMなど、実行環境に関する情報の取得・提供を担う。取得方法や出力データ型は別途設計する。
- **UI（将来）**: IMEとしての候補表示やユーザーとのやりとりを担う境界。OSへの確定文字列の反映を同じノードに含めるかは未決定。

**注意:** 「システムノード」は**必ず特権が必要**という意味ではない。固定文字列のInputやデバッグ用Outputのように、単純な処理を含む場合もある。逆に、キー入力・OS操作・機密情報などのアクセス制御は、分類名だけでなく実際に利用する**ホストAPIと権限**によって判断する。

システムノードを本体が提供することと、**外部作者が同種の入力・出力アダプターを開発できること**は両立させる。必要な権限や拡張APIは個別に設計する。

### 2. プリミティブノード（Primitive Node）

特定の日本語入力方式や高機能な変換アルゴリズムを前提とせず、**一つの明確な基本操作**を行う、再利用しやすい処理ノード。

- 例: 文字列の連結・置換、値の比較、条件分岐、Sequence/Choiceの生成、候補のフィルター、スコアの加算。
- **単純な内部実装を必須にはしない。** 重要なのは外部から見た責務が小さく、複数の異なるグラフで使い回せること。
- 本体が標準提供しても、利用者や第三者が同等のものを独自実装してもよい。
- 専用の「展開ノード」を必須にせず、候補木を走査・再構築する共通ライブラリも利用できるという既存方針を維持する。

### 3. 標準機能ノード（Standard Function Node）

**DIY_IME2側が標準で提供する**、利用目的が明確な機能単位の処理ノード。プリミティブを組み合わせて作っても、独立した複雑な実装で作ってもよい。

- 例: ローマ字→かな、辞書を利用した単語変換、かな漢字変換、形態素解析、校正、翻訳など。
- 「標準」とは**公式が提供・保守の対象として採用した**ことを指す。実行エンジンに機能をハードコードすることや、他の実装を禁止することではない。
- 同じ機能を第三者が別方式・別辞書・別モデルで実装し、利用者が差し替えられる余地を残す。
- この分類は、**すべての言語処理機能を標準搭載するという決定ではない。** 採用前のものは「標準機能ノード候補」と呼ぶ。既存のテスト用・実験用ノードも、存在するだけで自動的に正式採用扱いにはしない。

## 境界が曖昧な場合の判断順

1. **実行環境やOSとの境界を提供することが主目的か？** → システムノード。例: ホストからの文字入力、デバッグ出力、環境情報、IME UI。
2. そうでなければ、**意味が小さく、他の処理の材料として広く再利用する基本操作か？** → プリミティブノード。例: 文字列置換、候補の統合。
3. そうでなければ、**DIY_IME2が公式に提供する特定の実用機能か？** → 標準機能ノード。例: 辞書を用いたかな漢字変換。
4. それ以外の独自実装は通常の**外部・ユーザー作成ノード**として扱える。機能の大きさは標準機能ノードに相当していても、正式採用がないものを「標準提供済み」とは呼ばない。

**例:** 単に入力文字列を置換する操作はプリミティブ。ローマ字入力規則を解釈してひらがなを生成する処理は機能単位であり、公式採用すれば標準機能ノード。キーボードイベントをホストからグラフへ受け渡す境界はシステムノード。

## 分類と混同しない項目

- **IME実装前／IME実装後**: 実装フェーズを表す別軸。たとえばInput・Output・SpecはIME化前にも検討できるシステムノードであり、UIはIME化段階のシステムノード。
- **実装状態**: 候補・設計中・実験・正式採用・実装済み・検証済みを区別する。上の分類から実装の有無を推定しない。
- **配布場所・開発言語**: 本体リポジトリ／別のノードリポジトリ、Rust／他言語などは分類とは独立。ノードの共通APIと適切な権限境界を守る。
- **セキュリティ**: 権限や隔離を分類名から自動付与しない。実際に必要なファイル・ネットワーク・OS・ホストの操作権限から定義する。
- **グラフの機能的制約**: この文書はノードの用語を定義するものであり、現在の文章用Packet形式や、将来のIME用ポート型、具体的なNode APIは変更しない。

> **この文書で決めるのは3種類の言葉の意味だけ。** 個々のノードをどの種類で正式採用するか、配布するか、どの権限を与えるか、どのAPIを使うかは、別の設計・Issueで決める。
